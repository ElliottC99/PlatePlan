Ideation: Rescuing PlatePlan

Date: 2026-10-25Topic: plateplan-rescueMode: repo-grounded

Focus: Elliott's AI-Studio-built meal-planning app feels "too far gone" with "loads of parallel systems". Understand its current state, and find the cleanup directions most worth taking.

Short answer

It is not "too far gone". The app runs from one coherent tree (src/), most of its tests pass, and much of the "parallel systems" feeling comes from leftovers and churn rather than from rival live code. A lot of the leftovers can be deleted without changing behaviour. The real live duplication is a short, nameable list. The biggest risks are not the messy code. They are an unknown database security setting, no backup, and an editing workflow that keeps adding copies faster than anyone can remove them.

Grounding Context

Codebase Context

What the app is

  • A meal-planning PWA for one household (Elliott and Chloe). It covers Today, Planner, Recipe Vault, ingredient and product banks, Shopping, Data Quality, Settings, Sync, Tesco import and a plan generator.
  • It is plain browser ES modules with no bundler, served by a tiny Express server. Data lives in Firebase Firestore under a hard-coded households/elliott-chloe.
  • It was built entirely through Google AI Studio / Gemini chat and synced to GitHub. That produced 529 commits between 2026-07-21 and 2026-10-24, 311 of them in October.

What is genuinely wrong

  • Hand-kept bookkeeping. The version is typed by hand into many places, and the copies now disagree: package.json 3.35.4, sw.js v3.45.7, main.js?v=3.38.18, cache key v3.35.4, and a test expecting 3.30.0. Module header comments carry their own versions too, and the offline cache list is maintained by hand. RecipeWizardModal is imported by main.js but missing from sw.js. Commits titled "bump version" sometimes also carry real code changes (e.g. 602b05e).
  • Real duplicates still in use:
    • two plan generators (PlanGeneratorService, MealPlanGeneratorService)
    • two unit converters, both imported by RecipeIngredientParser.js
    • four Data Quality modules (~1,300 lines) with two separate lists of issue types
    • four places holding app state (store/coreState.js is the real one)
    • two copies of ActionSheetUI
    • two Firebase config blocks
    • two places the plan is read from (HydrationService.js:168: const plan = subcollPlan || legacyPlan;)
    • two to six modules writing each Firestore collection. For example, the products write appears word for word in both ProductRepository.js:61 and ShoppingFirestoreRepository.js:143.
  • Problems hidden or bypassed:
    • Startup errors are silently swallowed (main.js:323-325). One line, getState() = {} at HydrationService.js:225, is not valid code and only goes unnoticed because the error is caught and discarded.
    • About 160 places write window.* globals, and inline onclick appears 205 times even though ActionBridge exists to replace it.
  • No safety net worth the name. There is no CI, no lint and no smoke test. Two tests fail unnoticed. One file has a syntax error (src/views/PantryBankModalService.js:183), although nothing loads it.
  • Repo hygiene. cookies.txt is committed and there is no .gitignore. AI Studio leftovers are committed too (syntax_check.log, app/applet/).

What looks worse than it is

  • The old runtime is dead. scripts/core|features|services|ui and scripts/main.js are an older runtime that the HTML stopped loading on 2026-09-25 (00538fd). No test imports it either. The tests import src/.
  • Many "duplicate" files are one-line re-exports. They just pass through the real module (export * from …). At least three have no importers: utils/ActionBridge.js, components/recipe/VaultRecipeCard.js and views/ProfileAllocationCard.js. components/RecipeWizardModal.js and services/firebase.js show none either. Two others are still in use: services/InventoryRepository.js and services/PlanRepository.js, which HydrationService imports.
  • Two HTML shells, one copy. index.html and PlatePlan.html are byte-identical. It is one shell kept twice, not two apps.
  • Loaded but apparently unused. The analytics and prep components are loaded and exposed on window through componentRegistry.js, but no caller was found. Shopping can be routed to but has no button in the HTML nav. The Gemini feature is switched off (aiEnabled:false) with no call site.

Relation to the older PlatePlanner work

  • PlatePlanner main was a single ~4,100-line HTML file with state in localStorage.
  • The feat/bun-sqlite-persistence branch held an ideation, brainstorm and plan for a Bun + SQLite "file as document" backend. None of that survived; Elliott's line moved to Firestore instead.
  • Its advice to "normalise the schema, migrate from day one" is still the right answer to today's schema drift (idea 7).

How this happens

  • GitClear's 2025 data shows AI assistants add new blocks of code instead of reusing existing ones. Copy/paste rose about 8× while refactoring fell.
  • AI Studio users report these problems:
    • the model trusts stale chat history over the current files
    • it rewrites whole files
    • its GitHub sync is one-way and sometimes claims "In Sync" when changes never arrived
  • The sprawl is a predictable result of the tool plus a missing safety net. It doesn't mean Elliott did something wrong.

1. Secure and snapshot the household data first

Idea 1Axis: Data and state integrityConfidence 90%Complexity Low
Description

Before anyone touches code, do three things:

  1. Export households/elliott-chloe (every subcollection) to dated JSON, kept outside git.
  2. Read the security rules currently deployed in the Firebase console.
  3. Commit a firestore.rules and firebase.json that allow only the two household members' accounts.

Later, the rules can also reject badly shaped documents, for example recipe writes that use the legacy cal or prot fields.

Basis
  • direct: there is no firestore.rules or firebase.json anywhere in the repo.
  • direct: the household ID is hard-coded (src/config/firebase.js:8), the public API key appears in two files, and history shows an anonymous-auth flow (54c5aa4).
  • direct: startup can wipe local state with try { localStorage.clear(); } catch(e) {} (src/main.js:195).
  • direct: collections have several writers each.
  • external: vibe-coded apps commonly ship with open backend rules (Lovable CVE-2025-48757, Supabase RLS).
Rationale
Git can undo code changes, but nothing can undo lost or leaked household data. With a backup in hand, every later cleanup can be reversed, which lowers the fear holding Elliott back. The rules answer the one question that could outrank everything else: who can read or wipe this data right now?
Downsides
A full export needs the Firebase CLI or Admin SDK and console access, which only Elliott may have. Tightening the rules can lock the app out if the sign-in method doesn't match what the app actually uses, so test against a copy first.

2. One evidence-checked map of live, shim and dead code, then quarantine

Idea 2Axis: Parallel systems and dead weightConfidence 85%Complexity Low–Medium
Description

Build the map. Generate a ledger of every module, starting from the real entry points (index.html → src/main.js and sw.js), using knip or dependency-cruiser. Mark each module as one of:

  • live
  • live shim: a one-line re-export that something still imports
  • dead shim: a re-export nothing imports
  • loaded but uncalled
  • dead

Then name one owner per job: state, plan generation, unit conversion, Data Quality, Firebase init, each collection's writer.

Quarantine the dead code. Move what is proven dead into an attic/ that the build doesn't copy, and live with that for two weeks before deleting. The proven-dead list:

  • the old scripts/ runtime (keep build.js and the tests)
  • the dead shims
  • the unreferenced modules, including the one that fails to parse
  • FitScoreEngine
  • the AI Studio leftovers

Separately, untrack cookies.txt and add a .gitignore.

Basis
  • direct: src/utils/ActionBridge.js:6 is just export * from '../services/ActionBridge.js';.
  • direct: scripts/build.js:30 still copies scripts into dist/.
  • direct: the verifier confirmed that services/InventoryRepository.js and services/PlanRepository.js look like dead shims but are imported by HydrationService.js:11-12. A map, not a hunch, has to decide what goes.
  • external: knip and dependency-cruiser's no-orphans work on plain JS. Rescue playbooks say to delete unused files first, because that exposes further unused exports.
Rationale
This turns "loads of parallel systems" into a countable list that is mostly cheap to clear. It answers your question of whether it is as bad as he thinks with evidence rather than reassurance. Every later idea (canon, ratchet, consolidation) reads its "who owns what" from this map.
Downsides
Static analysis can't see globals reached through window.* or inline handlers. The "loaded but uncalled" category needs idea 6's census or a runtime check before anything in it is moved. The two-week attic period slows the visible win slightly.

3. Pin down "working": checklist, smoke test, real-data golden master, first known-good tag

Idea 3Axis: Safety net and verificationConfidence 80%Complexity Medium
Description

Elliott can't name a last-good version, and the version numbers can't identify one. The scheme reset from V2.6 to v3.x, and there have been three chat-driven rollbacks. So build "good" from the present instead:

  1. Write the checklist. Elliott writes a plain-English checklist of the household's week: sign in, see Today, generate a plan, open a recipe, build shopping.
  2. Automate it. Turn the checklist into one browser smoke test. It fails on the red crash overlay, on module import errors and on empty views, and it includes a node --check sweep.
  3. Record a golden master. Run the plan generator, shopping builder, fit score and recipe parser against idea 1's exported data, and save their outputs.
  4. Tag the result. Tag the commit that passes as known-good-1.

From then on, a reported bug becomes a failing check before anyone asks the AI to fix it.

Basis
  • direct: 0 tags in 529 commits.
  • direct: rollbacks were done by chat. 91b3aef "restore v3.3.0" added 25,471 lines.
  • direct: the fix-the-fix run c441d70 … 057f719 … 6691fd9 ("fuck fix", "fuck fix 2", "fuck fix 3").
  • direct: two live plan generators (PlanGeneratorModal.js:7 vs main.js:44/TodayView.js:19).
  • direct: the repository tests only exercise the "Firestore not initialised" path.
  • external: characterization / golden-master tests (Feathers, Working Effectively with Legacy Code). Record them on untouched code before an AI refactors anything.
Rationale
"Does it still do our week?" is a test a non-developer can judge, and it removes the need to dig for a good version in the history. Without the golden master, no one can safely merge the real duplicates, such as deciding which plan generator is right.
Downsides
Firebase auth has to be stubbed or test-accounted for the smoke test, which is the fiddliest part. The golden outputs encode today's bugs as well, so log known oddities (a QUIRKS.md) rather than "fixing" them inside the test.

4. Stamp, don't type: generate the version, offline cache list and second shell

Idea 4Axis: The change workflowConfidence 85%Complexity Low–Medium
Description

Stop humans and the AI writing version strings. A small build step:

  • derives one version from git and stamps it into the HTML meta, APP_VERSION and the sw.js cache names
  • generates the precache list from the real files with content hashes (workbox-cli injectManifest works without a bundler)
  • produces index.html from PlatePlan.html, so only one is edited

Then retire the per-module (vX.Y.Z) header comments and the "every change ends with a version bump" habit.

Basis
  • direct: 184 commit subjects say "bump version" (verified).
  • direct: bump runs touch 40–48 files each.
  • direct: PlatePlan.html (414 commits) and sw.js (383) are the two most-churned files.
  • direct: the versions disagree, as shown in the figure.
  • direct: RecipeWizardModal is missing from the sw.js precache list.
  • external: web.dev and Workbox document hand-versioned service workers as a known failure, and revisioned precache manifests as the fix.
Rationale
About a third of the history is bookkeeping, and every bump is another AI edit across dozens of files that can drift. A stale offline cache also produces "I fixed it but my phone still shows the old app", which reads as more breakage. This is the cheapest idea that cuts churn at its biggest source.
Downsides
It adds a real build step that Elliott's AI Studio flow must not bypass. If AI Studio deploys straight from source, the generated files need committing, or the deploy has to run the build.

5. A father/son operating model: AI Studio on a branch, a canon per chat, a green tick

Idea 5Axis: The change workflowConfidence 70%Complexity Medium
Description

Keep Elliott's tool, and change what reaches the live app:

  • Sync to a branch. AI Studio syncs to a studio branch, not main.
  • Automatic check. A GitHub Action runs idea 3's checks on every sync, plus a ratchet that fails only when things get worse than a committed baseline:
    • new duplicated blocks (jscpd --fail-on-new-clones)
    • new orphaned files (knip)
    • more window.* writes or inline onclick
  • Human merge. You (or the green tick) merge to main and tag good states.
  • Canon per chat. Each AI Studio chat starts fresh with a one-page canon pasted in: idea 2's owner table, a "never create another X; extend the owner" list, and a three-line brief (goal, files allowed, what to reuse).
  • Replace the size rule. The module-size rule becomes an ownership rule.
Basis
  • direct: 93646c9 "unify state access" changed 117 files (+1,162 / −14,960) straight onto the main line. The "fuck fix 1–3" run landed the same way.
  • direct: .github/ does not exist.
  • direct: the repo's own size rule is real but pushes toward more files. Audit_Report_v3.20.md:10 says "strictly under the 400-line ceiling" and about ten module headers say "Strictly modular (<350 lines)". Meanwhile modules grew from 144 (v3.20 audit) to 230, with unreferenced split fragments such as CategoryManagerOperations.js.
  • external: AI Studio forum reports. The model trusts stale chat history, rewrites whole files, and the GitHub sync is one-way and sometimes claims "In Sync" falsely. Users' prompt-only workaround rules are about 80% reliable. Instructions advise; checks enforce.
  • external: jscpd, knip and dependency-cruiser baselines.
Rationale
The sprawl is produced by the process, so a one-off cleanup will grow back unless the process changes. This gives each of you a defined role. Elliott keeps building. You review red or green, not code. The AI gets a map instead of guessing each session.
Downsides
It depends on whether AI Studio can target a branch in Elliott's setup (a question for him). A merge gate adds friction he may resist. Ratchet tooling needs an initial baseline and a little tuning to avoid false alarms.

7. One door per Firestore collection; Data Quality becomes a report

Idea 7Axis: Data and state integrityConfidence 65%Complexity High
Description

Most Data Quality issue types (drift, desync, incomplete, orphan) exist because several modules write the same collection in different shapes. Fix the cause:

  • give each collection exactly one repository that normalises on write to one schema
  • add a schemaVersion
  • run a one-time migration on the exported data
  • redirect every other writer through that one repository
  • collapse the old-and-new fallback chains and the hard-coded household constants into one config module

Data Quality then shrinks to a read-only report on genuinely human data issues: duplicates and missing densities.

Basis
  • direct: RecipeFirestoreRepository.js:15 reads r.macros?.calories ?? r.macros?.cal ?? r.calories ?? r.cal ?? 0, and DataQualityEngine.js:41 repeats the same chain.
  • direct: the identical products write in ProductRepository.js:61 and ShoppingFirestoreRepository.js:143.
  • direct: ingredients are written from about six repositories.
  • direct: the legacy-or-subcollection plan read at HydrationService.js:168.
  • direct: preference fallbacks such as legacyPrefs.elliottCal ?? legacyPrefs.ecal ?? 2100.
  • external: your own PlatePlanner plan ("normalised schema, migrations from day one").
Rationale
This is the largest single simplification on offer. It removes the reason a ~1,300-line repair subsystem exists, and it stops the next AI session reintroducing drift in whichever duplicate writer it happens to edit.
Downsides
It is the riskiest idea, because it touches live data and many files. It should only start after ideas 1–3 exist (backup, map, golden master), and it is best done in slices: one collection at a time, starting with recipes.
